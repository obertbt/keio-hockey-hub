# 速さと、押した手ごたえ

「全体的に重い。押したのか分かりづらい」という声から手を入れたものの記録です。

この2つは別の問題です。分けて考えないと、片方しか直りません。

| 言われたこと           | 本当の原因                            | 直し方                 |
| ---------------------- | ------------------------------------- | ---------------------- |
| 押したのか分かりづらい | 押しても**画面が1ドットも変わらない** | 手ごたえを足す（体感） |
| 全体的に重い           | 中身が出るまでの往復が多い            | 往復を減らす（実時間） |

体感のほうが効きます。**同じ0.8秒でも、押した瞬間に何か動けば速く感じます。**
先に体感から書きます。

---

## 1. 押しても何も起きなかった

`globals.css` にこれが入っていました。

```css
-webkit-tap-highlight-color: transparent;
```

端末が勝手に出す灰色の四角を消す指定です。意図は分かります。
**ただし、代わりを置いていませんでした。**

さらに、ボタンの見た目は `hover:` だけで書かれていました。
**指で触る画面に hover はありません。**

つまりスマートフォンでは、

- 端末の反応 … 消してある
- こちらの反応 … 書いていない

押しても、何も、起きない。
届いていないと思ってもう一度押す。二度押しはさらに遅いので、余計に重く感じます。

### 置いたもの

```css
@media (hover: none) {
  a:active,
  button:active:not(:disabled) {
    transform: scale(0.97);
    filter: brightness(0.94);
  }
}
```

ほんの少し沈んで、少し暗くなる。それだけです。0.06 秒。
**速いほど「反応した」に見えます。** 遅いと今度は動作そのものが重く見えます。

あわせて `touch-action: manipulation` を入れました。
端末が「ダブルタップで拡大かもしれない」と待つ時間が無くなります。

動きを減らす設定にしている人には沈ませません（`prefers-reduced-motion`）。
色だけで伝えます。

## 2. 押したあと、待っている間も何も起きなかった

手ごたえは指を離すまでです。**待ち時間はそのあとに来ます。**

この画面はほとんどがサーバー側で作られるので、
リンクを押してから中身が出るまで、必ず往復が1回入ります。
その間、画面は押す前とまったく同じでした。

`components/ui/link.tsx` を作り、`next/link` の代わりにこれを使います。

- 画面のいちばん上に細い帯を出す
- 押したリンク自体を少し薄くする（どれを押したか分かるように）

帯は**8割で止めて待ちます**。端まで行くと「終わった」に見えるためです。
進み具合は出しません。何割まで来たかは分からないので、出せば嘘になります。

> 新しくリンクを書くときも `next/link` ではなく `@/components/ui/link` から。
> 混ざると、そこだけ手ごたえが無くなります。

フォームの送信ボタンは、もともと `useFormStatus` で
「保存しています…」に変わるようにしてあります。そちらはそのままです。

## 3. 中身が出るまでの往復が多かった

ここからは実時間の話です。画面を1枚出すのに、こうなっていました。

```
proxy          getUser()              → Auth サーバーへ往復 ①
ページ         getUser()              → Auth サーバーへ往復 ②
getAppSession  profiles               → 往復 ③
               team_members           → 往復 ④（③ の答えが要る）
               member_permissions     → 往復 ⑤（④ の答えが要る）
ページ本体     その画面のデータ        → ここでやっと本題
```

**中身を1文字も出さないうちに5往復。**
③④⑤ は前の答えが無いと次を聞けないので、並べることもできません。

スマートフォンの回線だと、この5回がそのまま待ち時間になります。

### ①② を減らす

`getUser()` を `getClaims()` に変えました。
Cookie の中の署名をその場で確かめるので、
鍵が公開鍵方式なら**通信が起きません**。

安全性の話は [security.md の 17-8](security.md) に分けて書きました。
要点だけ:

- 共通鍵方式のままなら、これまでどおり聞きに行く（**緩くはならない**）
- 公開鍵方式に切り替えると、往復2回が消える
- RLS の `auth.uid()` は、もともと同じ JWT を信じている

**公開鍵方式への切り替えは Supabase の管理画面から行います**
（Authentication → JWT Keys）。切り替えなくても動きますが、
この2往復は残ります。いちばん効く1手なので、やっておくことをおすすめします。

### ③④⑤ を減らす

`current_session()` を足しました（migration 0029）。
プロフィール・所属・個別の権限を**1回で返します**。3往復が1往復になります。

RLS を通らない関数なので、引数を取らない形にしてあります。
「誰の素性か」を外から指定できるようにすると、他人を引ける関数になるためです。

### 結果

```
proxy          署名をその場で確認      → 通信なし（公開鍵方式のとき）
ページ         同上（同じ要求内で使い回し）
getAppSession  current_session()      → 往復 ①
ページ本体     その画面のデータ        → 往復 ②（画面ごとに並べて取得済み）
```

5往復 → 1往復。画面ごとのデータ取得は、もともと `Promise.all` で並べてあります。

## 4. やらなかったこと

- **読み込み中の骨組み（skeleton）を画面ごとに作る**
  `app/(app)/loading.tsx` に1つだけあります。増やすと、画面ごとに
  「骨組み → 中身」の2回ぶんちらつきます。いまは帯のほうが静かです。

- **データを手元に貯めておく（キャッシュ）**
  日報やコンディションは「いま出したか」が大事なので、
  古いものが一瞬でも出ると困ります。速さのために正しさを崩さない。

- **画面を減らす・項目を減らす**
  これは速さの問題ではないので、別に扱います。

---

## 5. 次に重くなったときの見かた

1. **押した瞬間に何か動くか。** 動かないなら、それは速さの問題ではない
2. **中身が出るまでに何往復あるか。** 順番待ちになっている往復を探す
3. 往復を減らせないなら、**待っていることを見せる**

順番はこのとおりです。3 から入ると、たいてい直りません。
